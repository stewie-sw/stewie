# Release policy & evidence (PO-13)

This page is the authoritative SemVer policy for STEWIE and documents the **release-evidence manifest**
that aggregates the objective release evidence from the live tools.

## Versioning (SemVer 2.0.0)

STEWIE follows [Semantic Versioning 2.0.0](https://semver.org/spec/v2.0.0.html), as declared in
`CHANGELOG.md` (Keep a Changelog format).

**Single version source.** The version is `stewie.__version__`, which **must equal** `pyproject.toml`
`[project].version`. The equality is enforced by `stewie/server/test_version.py` and re-checked by the
release-evidence manifest (`version.in_sync`); a drift fails CI.

**Public API** (what a version bump is measured against):

- the FastAPI HTTP routes the cockpit and external clients call,
- the cockpit contract (`web/assets/adapters.js` view models over the FS-02 spine contracts),
- the importable Python surface of `stewie` / `dart` / `lode` / `leap` / `forge`,
- the persisted schema versions (mission / profile / Plan-IR, PO-09).

**Bump rules**

- **PATCH** (`0.0.x`): bug fixes and internal changes with no public-API change.
- **MINOR** (`0.x.0`): backward-compatible additions to the public API.
- **MAJOR** (`x.0.0`): backward-incompatible public-API changes.

**0.x pre-release rule.** While the version is `0.x`, the public API may change between MINOR releases.
`0.x` is a **trainer / simulator** surface, not a production flight-autonomy release (PRD §0); breaking
changes are noted in `CHANGELOG.md` but do not force a MAJOR bump until 1.0.0.

**When 1.0.0 is cut.** 1.0.0 is tagged once the §4.2 release blockers (RB-01..06) are cleared and the
PO-/N-series operations requirements reach `I=X=V=D` in the PRD §7 matrix.

## Release-evidence manifest

`release_manifest.json` (repo root) is generated by `scripts/gen_release_manifest.py` and aggregates the
**objective** release evidence — no hand-entered numbers; every field is sourced from a live tool or a
real artifact, listed under `sources`:

| Field | Source |
|---|---|
| `version` (+ `in_sync`) | `stewie.__version__` vs `pyproject [project].version` |
| `req_trace` | `scripts/req_trace.py` (PRD §7 reconciliation; `reconciles` ⇔ no `v_done_uncited`, no orphan markers) |
| `autonomy_gate` | `scripts/release_gate.py` (AS-01..17 status) |
| `sbom` | `scripts/gen_sbom.py` (CycloneDX component count from the pinned lock) |
| `dependencies` | `scripts/check_deps_lock.py` (pyproject ⇄ lock drift, per lock) |
| `changelog` | `CHANGELOG.md` (documents the version, Keep-a-Changelog + SemVer declared) |
| `semver_policy` | this file's presence |

**Deterministic vs volatile.** The committed `release_manifest.json` holds only **deterministic** fields
— those change only when the matrix / deps / version / docs change. The **volatile** fields
(`generated_at`, the git `commit`, live `coverage` / `tests`) are *excluded* from the committed file (they
would make it perpetually stale) and are written by `--full` to the reports dir at release time.

### Commands

```bash
python3 scripts/gen_release_manifest.py          # (re)write the committed deterministic manifest
python3 scripts/gen_release_manifest.py --check   # CI guard: exit 2 if release_manifest.json is stale
python3 scripts/gen_release_manifest.py --full     # release-time: + commit + live coverage/tests → reports dir
```

`--check` runs in CI so the committed manifest cannot silently drift from the tools — the same honesty
gate `scripts/gen_status.py` uses for `STATUS.md`.

## Release checklist

1. Update `CHANGELOG.md` (move Unreleased → the new version, dated).
2. Bump `stewie.__version__` **and** `pyproject [project].version` together (they must stay equal).
3. `python3 scripts/gen_release_manifest.py` → commit the refreshed `release_manifest.json`.
4. Confirm `release_manifest.json` shows `req_trace.reconciles = true`, `dependencies.all_ok = true`,
   `version.in_sync = true`.
5. `python3 scripts/gen_release_manifest.py --full` to capture commit + live coverage/tests for the record.
6. Tag the release.
